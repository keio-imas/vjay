# Native movie transfer and playback validation — 2026-11-22

VJAY v0.3.0, Apple M2 Pro / Metal, macOS 26.4.1, Rust 1.99.1, FFmpeg 8.1.2. This change groups files by responsibility within
all three layer crates and replaces the selected macOS movie path with persistent
VideoToolbox decoding and native Metal texture transfer. Application and domain remain
independent of GPUI, wgpu and operating-system branches.

The implementation was subsequently packaged as **v0.3.1**. The measurements and
functional checks below preceded that version-only bump.

## Measurement method

The same Release executable compares the existing FFmpeg VideoToolbox/RGBA adapter
(`legacy`) with the injected Metal movie adapter (`native`). Both run the same
`sample/anime-club.vjay.json` graph, with two different generated 3840×2160, 60 fps,
4-second H.264 8-bit 4:2:0 files at 24 Mbit/s. Node previews are disabled, no audio
backend is injected, and no output window is created. Render extents are 1920×1080
and 3840×2160. Each case warms five frames at time zero before recording.

Three runs per adapter and extent alternate adapter order. No compilation or other
VJAY GPU test runs during measurements. Workloads execute sequentially:

- `sequential`: 120 exact frames at i/60 seconds.
- `jog`: 120 requests cycling normalized positions 0.5, 0.502, 0.5, 0.498 on deck A,
  with complementary positions on B. On these sources this repeatedly visits a few
  adjacent frames, exercising a small working set. It is not random seeking.
- `seek`: 16 requests cycling 0.85, 0.15, 0.65, 0.35, 0.95, 0.05, 0.75, 0.25, with
  complementary positions on B. This exceeds the four-entry requested-frame cache
  and includes cold long-GOP reference decoding.

Every timed frame includes `Session::render_at` and `wait_idle`: the latter submits
an empty fence and waits for GPU completion without reading pixels. Reported times
are fenced headless end-to-end latency, including decoder delivery and command
submission. They are **not presentation FPS, GPU timestamps, display jitter, or a
claim of sustained 60 fps desktop operation**. `over_16_67_ms` counts requests whose
fenced latency exceeds that budget; it does not count dropped presented frames.

`video_cpu_bytes` counts delivered RGBA payload in the portable decoder adapter,
not memory-controller traffic or all CPU copies. Native playback reports zero because
decoder planes are mapped to Metal, converted and scaled on the GPU. Compressed sample
handling, metadata probing and compatibility-cache preparation still use the CPU.
The benchmark performs no image capture. Pixel assertions belong to separate GPU tests.

Raw results: [CSV](playback-2026-11-22.csv). Rows contain within-run percentiles;
summary values use the median of the three corresponding run percentiles.

## Results

| Extent | Workload | Legacy p50 / p95 / p99 (ms) | Native p50 / p95 / p99 (ms) |
| --- | --- | ---: | ---: |
| 1920×1080 | sequential | 11.54 / 15.55 / 17.38 | 8.26 / 12.10 / 14.06 |
| 1920×1080 | jog | 268.70 / 296.57 / 321.63 | 1.89 / 3.59 / 6.47 |
| 1920×1080 | seek | 546.32 / 1016.22 / 1016.22 | 24.94 / 221.38 / 221.38 |
| 3840×2160 | sequential | 42.57 / 62.61 / 73.61 | 11.94 / 17.17 / 19.66 |
| 3840×2160 | jog | 300.78 / 348.81 / 374.97 | 4.64 / 6.71 / 7.59 |
| 3840×2160 | seek | 753.47 / 2060.95 / 2060.95 | 31.24 / 218.43 / 218.43 |

For 120 sequential requests at 4K, the legacy adapter delivered 7,896,268,800 bytes
of RGBA payload; native movie delivery used **0 CPU pixel bytes**. For nearby jogging,
legacy restarted the FFmpeg decoder 60 times per run; native started no new hardware
sessions and recorded 119 requested-frame cache hits. The eight-target seek workload
repositioned compressed readers 25 times in native mode while keeping both sessions.

Native 4K sequential workloads still exceeded 16.67 ms on 6–9 of 120 fenced requests
per run. Nearby jogging had 0–1 such requests; every cold-seek request exceeded the
budget. These results support lower transfer/seek overhead, not a universal 4K60 guarantee.

Both native sources retain their hardware decoder sessions across the tested seeks.
A native seek reset repositions the compressed sample reader; it is different from
starting a new decoder process/session. Metrics in the CSV are differences from the
start of each workload, so initial decoder creation is outside the timed counts.

## Previously reported 4K source

The previously supplied 3840×2160 H.264 10-bit 4:2:2 MOV (24000/1001 fps,
10.116958 seconds) was also opened read-only through the compatibility-cache path.
Both decks used that source at a 4K render extent. All three workloads completed
with zero delivered CPU pixel bytes and no new hardware sessions after warm-up.
Source SHA-256, file size and modification time matched before and after the run.
The source and its path are not included in this repository. This is a separate
single-run compatibility check, not part of the generated-fixture comparison.
Its initial compatibility-cache preparation is outside the timed window.

Raw results: [compatibility CSV](playback-compatibility-2026-11-22.csv).

## Correctness and stability

- Workspace tests cover graph deletion, signal slots, controls, file selection,
  persistence, nested patches and transport behavior.
- Native image tests exercise H.264, H.264 with B-frame reordering, HEVC Main10 and
  ProRes, checking red/blue frame transitions, backward/end seeks, cache reuse and
  one hardware session per source. HEVC `hev1` sample entries are normalized to
  `hvc1` without recoding compressed data.
- The anime-club and Loadable Video integration tests use the native adapter, checking
  file switching, seek feedback, crossfade and blackout pixels.
- Asynchronous delivery is tested under continuously advancing requests and looping;
  source deletion reaps workers outside the UI thread.
- Ordinary parameter edits update dense cells without rebuilding the execution
  schedules. The open-extension test verifies that parameter-selected shaders still
  recompile. Prepared images retain their existing preparation behavior.
- Deadline pacing tests cover 600 frame slots, render-work exclusion, overrun skipping
  and rate changes. Clock tests cover recovery after a one-second UI stall. Interior
  seek positions no longer receive an endpoint offset; 1,000 small jogs preserve f64
  time precision rather than accumulating normalized f32 rounding error.

The desktop loop still executes rendering on the GPUI thread. Thirty-Hz routine
editor notifications and fixed deadlines reduce avoidable work but do not isolate
rendering from every expensive UI action. Native movie output is 8-bit SDR; HDR tone
mapping and a complete color-managed workflow are not implemented. Long cold seeks
still take reference decoding time. Eight-source playback, multiple physical 4K
projectors, and long-session thermal behavior are not measured here. Windows/Linux
do not have this native movie PAL or a validated native desktop presentation backend.

## Reproduction

Generate two independent test clips (requires macOS hardware H.264 encoding):

```sh
ffmpeg -v error -f lavfi -i 'testsrc2=size=3840x2160:rate=60:duration=4' \
  -c:v h264_videotoolbox -allow_sw 0 -b:v 24M -pix_fmt nv12 /tmp/vjay-a.mp4
ffmpeg -v error -f lavfi -i 'testsrc2=size=3840x2160:rate=60:duration=4' \
  -vf hue=h=90 -c:v h264_videotoolbox -allow_sw 0 -b:v 24M -pix_fmt nv12 /tmp/vjay-b.mp4
cargo build --release --example playback_bench
# Run alternately, three times each, after compilation is idle.
target/release/examples/playback_bench /tmp/vjay-a.mp4 /tmp/vjay-b.mp4 3840x2160 120 legacy
target/release/examples/playback_bench /tmp/vjay-a.mp4 /tmp/vjay-b.mp4 3840x2160 120 native
# Repeat with 1920x1080.
```

Native movie regression tests require Metal, VideoToolbox and FFmpeg:

```sh
cargo test -p vjay-infrastructure --test native_movie --test anime_club --test loadable_video \
  -- --ignored --test-threads=1
```
